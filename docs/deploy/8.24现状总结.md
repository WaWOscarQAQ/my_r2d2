# r2d2 实现进展

## 论文重点总结

### 论文对 fuzz 的贡献

- ROS 节点通过消息通信，一个节点内又有多个回调。
- 相同的一组回调即使覆盖相同代码，也可能因消息处理顺序、回调调度顺序和时间不同而处于不同状态。
- R2D2 使用 `callback trace` 描述回调交互的时间序列，并同时观察回调执行时长和消息吞吐量。

### ROS2 callback 调研

- 追踪信息分布在多层：从上到下包括 `RCLCPP`、`RCL`、`DDS`，需要收集每一层的 callback 信息；
- `RCLCPP` 执行器调度回调；回调响应 topic 消息或 service 请求。
- 回调随不同消息到达而形成的时间顺序就是 callback trace。

### 论文方法

#### 插桩与 tracer

- 在 `RCL` 和 `RCLCPP` 运行时层插桩，同时采注册期事件和执行期事件。
- Registration Tracer 记录 `callback name`、`namespace`、`callback type`、`rclcpp handler`、`rcl handler`，负责把两层注册信息拼成 `callbackinfo`。
- Runtime Tracer 记录 `executor execute`、`callback start/end`、`rcl take` 对应的 `handler`、`timestamp`、`buffer size`、`pub/sub time`，负责恢复 `call trace`、`msg trace`、执行时延、调度时延和吞吐量。

#### callbackinfo构建

```
Callback Registration Info
  Callback ID        = Hash(Callback name, Callback type)
  Callback Handlers  = Union(Rclcpp handler, Rcl handler)

Runtime Execution Info
  Callback ID        = CallbackInfo.find(Rclcpp handler)
  Execution Latency  = Duration(Start time, End time)
  Scheduling Latency = Duration(Invoke time, Start time)

  Callback ID        = CallbackInfo.find(rcl handler)
  Throughput          = Buffer size / Duration(Pub time, Sub time)

Callback Trace Info
  CallTrace = Vector<Callback Latency>
  MsgTrace  = Vector<Message Latency>
```

#### Callback Trace 构建

R2D2 持久维护两个全局结构：

- `Global Callback Graph`：保存回调调用的时间先后关系。
- `Global Callback Latency`：保存每个已见回调的平均时延和每种消息的平均吞吐量基准。

新状态满足以下任一指标：

- 全局 callback graph 中出现新边：当前轮里相邻两个 callback ID 形成的有序边，之前没在全局图里出现过。
- 某个回调的时延显著偏离已有平均基准：论文只公开了“显著偏离基准”，没有公开具体统计公式。
- 某种消息的吞吐量显著低于平均基准：论文只公开了“显著低于基准”，没有公开具体统计公式。

上述基准值通过 2 小时的 dry run 获得，这个过程也顺便收集到了 callback 函数信息。

#### 结果反馈变异机制

- payload pool 为空：从提取的接口中随机选一个，按规格生成载荷。
- payload pool 非空：选择此前触发新状态的载荷，根据接口规格的数据文件递归变异。
- 执行后若触发 crash 或新状态，就把载荷保留到池中，供未来继续变异。

论文没有给出如何进行引导变异，以及具体变异手段。

## 项目复现情况

### 插桩与 tracer

- 相同：tracer 已落在 `rclcpp/rcl` 运行时层。
- 相同：已采 `rclcpp_callback_init`、`rcl_callback_init`、`executor_execute`、`callback_start`、`callback_end`、`rcl_take` 六类事件。
- 相同：注册事件和运行时事件分开采，能同时恢复回调注册关系和执行链路。
- 差异：共享内存布局、字段容量、ABI 版本属于复现实现细节，不是论文公开设定。

### callbackinfo构建

- 相同：按 `Hash(callback name, callback type)` 建 `callback ID`，再用 `rclcpp/rcl handler` 关联两层记录。
- 相同：执行时延用 `start/end`，调度时延用 `invoke/start`，消息吞吐用 `buffer size / (sub - pub)`。
- 相同：`namespace` 已进入注册信息采集。
- 差异：当前 hash 算法是 `FNV-1a 64`，这是仓库自定值，不是论文公开值。
- 差异：`namespace` 被记录但不进入 `callback ID`；若同一 `(name, type)` 跨 namespace 冲突，当前实现会直接判该 trace 失去状态分析资格，这条防护是复现补丁。

### Callback Trace 构建

- 相同：持续维护全局 `callback graph` 和 benchmark reference。
- 相同：每轮先聚合当前轮重复 callback/message，再做状态判定，不直接拿原始事件流判定。
- 相同：benchmark 仍采用独立预采样阶段，默认时长是 `7200s`。
- 相同：live 闭环现在是“发送输入 -> 真实系统执行 -> 连续 drain 到静默收敛 -> 构建当前轮 trace”。
- 差异：live 轮次边界已不再依赖 `RoundBoundary marker`；该 marker 还留在 tracer ABI 里，但不再作为真实闭环判定边界。
- 差异：论文只公开了“新边 / latency 偏离 / throughput 下降”三类证据，没有公开显著性公式；当前仓库已合并为单一 callback-trace verdict，阈值仍是显式复现参数。
- 历史差异：2026-08-24 时 benchmark 阶段还只发送 `topic/service`，不把
  `parameter` 混进基准阶段。当前合并路线已改为 topic/service/action/safe
  parameter profile 使用同一 live binding 集合；parameter 轮后 restore，恢复期
  trace 不进入本轮判定。

### 结果反馈与变异

- 相同：`payload pool` 为空时随机选接口生成输入；非空时从已触发新状态的输入继续变异。
- 相同：只有触发 `crash` 或 `new state` 的输入才会留在池中。
- 相同：变异仍按接口规格递归下钻，不是纯字节级乱变。
- 差异：论文没有公开接口选择分布、池项选择分布和具体变异算子；当前实现显式采用均匀选择和仓库自定义递归变异。
- 差异：`parameter` 发送与恢复属于当前复现扩展，不是论文公开的 benchmark 输入面。

### 整体流程

- 相同：输入已经通过真实 ROS 接口发到真实系统，再从 `rclcpp/rcl` 层连续收 trace，不走 mock。
- 相同：当前已具备 `topic`、`service`、`parameter` 三类真实 sender。
- 相同：`parameter` 集合不再手写固定表，而是按源码动态参数集合与 live `/costmap` 已声明参数求交后生成。

- 差异：`action` sender 还没落地。
