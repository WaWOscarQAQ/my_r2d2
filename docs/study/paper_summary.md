# 《Enhancing ROS System Fuzzing through Callback Tracing》精读

- 论文：Yuheng Shen 等，ISSTA 2024
- 系统：`R2D2`
- 核心问题：代码覆盖率难以区分 ROS 中“执行了相同代码、但回调顺序和时延不同”的运行状态。
- 核心方法：把回调执行顺序、回调执行/调度时延和消息吞吐量组成 `callback trace`，以它代替代码覆盖率反馈来指导输入生成。

## 1. 摘要结论

**机制概括**

R2D2 在 ROS 运行时中系统化插桩，实时收集回调与消息交互，将其归纳为当前系统状态，再优先变异能够触发新状态的输入。论文在 Navigator2、TurtleBot3、Turtlesim 和 Autoware 上评估：相对 Ros2Fuzz、RoboFuzz 的平均代码覆盖率提升分别为 `3.91x`、`2.56x`；发现 39 个此前未知的缺陷，其中 6 个已修复；论文汇总的平均执行时延和内存开销分别为 `10.4%`、`1.0%`。

> 机器人操作系统 2（ROS）是机器人软件开发事实上的标准，并广泛应用于各种安全关键领域。许多测试工作致力于提供更安全的 ROS 代码库。然而，现有测试方法通常无法捕获 ROS 部署中固有的复杂且有状态的行为，因而测试效果有限。本文提出 R2D2，一种利用 ROS 运行时状态作为引导、以提高模糊测试有效性和效率的 ROS 系统模糊测试器。与传统模糊测试器不同，R2D2 采用系统化插桩策略，捕获系统运行时行为并实时刻画当前系统状态。这种方法能够更深入地理解系统行为，从而更有洞察力地探索 ROS 广阔的状态空间。我们将其应用于四个知名 ROS 应用进行评估。评估结果表明，与包括 Ros2Fuzz 和 RoboFuzz 在内的先进 ROS 模糊测试器相比，R2D2 的代码覆盖率分别提高了 3.91 倍和 2.56 倍，同时在 ROS 运行时和 ROS 应用中发现了 39 个此前未知的漏洞，其中 6 个已被修复。在运行时开销方面，R2D2 的平均执行开销和内存使用开销分别为 10.4% 和 1.0%，这使 R2D2 能够有效用于 ROS 测试。

## 2. 为什么代码覆盖率不足

### 2.1 回调顺序和时间构成代码覆盖率看不见的状态

**机制概括**

ROS 节点通过消息通信，一个节点内又有多个回调。相同的一组回调即使覆盖相同代码，也可能因消息处理顺序、回调调度顺序和时间不同而处于不同状态。R2D2 因此使用 `callback trace` 描述回调交互的时间序列，并同时观察回调执行时长和消息吞吐量。

> 然而，主要依赖代码覆盖率被证明并不适合 ROS 测试。ROS 是一个分布式系统，节点通过消息传递进行通信，每个节点都承载多个回调，以响应不同的消息或事件。ROS 中相当一部分逻辑和状态转换发生在这些回调之内，处理范围从传感器数据处理一直到执行器控制。代码覆盖率虽然衡量了已执行代码的范围，却可能忽略 ROS 中执行的质量或上下文。不同的消息处理序列可能执行同一组回调，但采用不同顺序或处于不同系统状态，从而产生仅凭代码覆盖率无法观察到的不同行为和潜在漏洞。以机械臂为例，同一组运动指令因回调顺序和时机不同，可能造成截然不同的物理结果；它们具有相同的代码覆盖率，而代码覆盖率无法捕获这种差异。
>
> 为解决这一局限，我们提出使用回调轨迹指导 ROS 系统模糊测试。回调轨迹表示回调交互的时间序列，能够更详细地揭示回调执行时长和消息吞吐量等方面。代码覆盖率在不同输入之间可能几乎没有变化，而回调轨迹可以更准确地指示系统内部状态转换。在模糊测试期间利用回调轨迹，可以更深入地理解系统状态转换，进而发现能够触发更多系统行为的输入并提高模糊测试性能。

### 2.2 两个核心挑战

**机制概括**

1. 自动、实时地跨 RCLCPP、RCL、DDS 等层收集分散的回调注册、调度、执行和消息传递信息。
2. 从当前回调轨迹中判定输入是否触发了新状态，再用这一状态反馈从 ROS 巨大的结构化输入空间中生成高质量输入。

> 引入回调轨迹涉及两个关键挑战：在 ROS 易变且异步的环境中捕获并理解状态转换，以及依据这些状态变化生成高质量载荷。第一，准确刻画 ROS 系统的状态转换，需要一种能够实时捕获和分析系统交互的方法；ROS 易变、异步的特性以及多样的应用组件使这一任务变得困难。现有从 ROS 自动获取此类状态信息的方法不足以处理这种多样性，它们要么需要人工规格说明，要么无法实时提供此类信息。此外，由于 ROS 的分布式特性，消息处理或回调调度等信息分布在不同系统组件中；收集这些信息需要深入理解 ROS 架构。因此，需要一种自动化方法，在测试期间准确刻画系统交互，从而反映 ROS 的状态。
>
> 第二，提高系统状态探索能力并实现有效模糊测试，需要一种利用状态变化生成高质量载荷的方法。然而，ROS 的输入空间十分广阔，因为它部署在多样环境中，需要响应各种传感器数据、控制命令和用户配置。以往模糊测试方法主要依靠代码覆盖率或人工推导的预言来指导输入生成。这种方式可能无法捕获整个系统的多方面行为，例如执行时长和调度顺序的变化，因而无法高效探索 ROS 系统状态空间。因此，必须分析收集到的交互行为并将其作为引导，生成高质量载荷，以更充分地探索 ROS 中的复杂行为并发现此前可能被忽略的问题。

### 2.3 R2D2 的总体解法

**机制概括**

R2D2 完全移除代码覆盖率反馈，形成三段式闭环：运行时插桩收集交互；由执行时长、调度和消息吞吐量构建回调轨迹；识别触发新状态的输入并提高其后续执行和变异优先级。

> 为解决上述挑战，我们提出 R2D2，一种面向整个 ROS 系统、由回调轨迹引导的模糊测试器。R2D2 按以下过程执行模糊测试。首先，为更好地理解系统行为，R2D2 在 ROS 运行时的不同组件中插入定制跟踪器，以系统地收集执行交互。随后，R2D2 根据收集到的交互刻画回调轨迹；其中包含回调执行时长、执行器调度操作和消息吞吐量，用于表示 ROS 的状态转换。进一步地，为生成高质量载荷，R2D2 在测试期间分析回调轨迹，识别触发新系统状态的输入，并指导高质量输入的生成。这种基于反馈的测试用例生成方式能够产生质量更高的输入，提高 ROS 系统模糊测试效率。

## 3. ROS 架构与已有测试方法

### 3.1 图 1：跟踪信息为什么分散在多层

**图中细节**

- 最上层 `ROS 2 Applications` 画出三个虚线 Node。节点内包含 Publisher、Subscriber、Client、Service Callback；节点之间通过绿色椭圆形的 `Topic` 和 `Service` 相连。
- `ROS 2 Runtime` 从上到下依次包含语言客户端库 `RCLCPP / RCLPY / RCLJAVA`、公共客户端库 `RCL` 与中间件接口 `RMW`、DDS 实现 `FastRTPS / CycloneDDS / eProsima`。
- 最底层是 `Linux / Windows / MacOS / RTOS`。这说明应用回调、客户端库地址和 DDS 消息传输信息天然位于不同层。

**机制概括**

RCLCPP 执行器调度回调；回调响应 topic 消息或 service 请求。回调随不同消息到达而形成的时间顺序就是 callback trace，它反映系统运行时行为和状态。

> 机器人操作系统 2（ROS）是一个开源软件栈，已经成为开发各类机器人系统事实上的标准。图 1 展示了 ROS 系统的总体架构。具体而言，ROS 系统主要由 ROS 应用和 ROS 运行时两部分组成，并且可以部署在 Linux、MacOS 和各种 RTOS 等多种操作系统上。
>
> ROS 运行时作为系统骨干，提供消息传递和回调调度等基础 ROS 功能。ROS 运行时采用多层结构。其顶层包含 RCLCPP、RCLPY 和 RCLJAVA 等多种客户端库实现，这些库以不同语言提供 API 实现，支持更高层应用开发。顶层之下是 ROS 客户端库 RCL，它为上述 API 实现提供标准接口。为了兼容底层不同的数据分发服务（DDS）实现，RCL 依赖 ROS 中间件接口 RMW 作为中间桥梁，从而实现分布式组件之间的高效通信。FastRTPS、CycloneDDS 和 eProsima 等不同 DDS 实现，为 ROS 提供不同的消息处理和服务质量机制。
>
> ROS 应用用于执行特定任务。通常，每个应用由多个节点组成，每个节点拥有不同回调，回调之间通过话题和服务通信。节点负责一个单一的模块化用途；节点内的回调则是在收到消息或服务请求等特定事件时被调用的函数。这些回调由 RCLCPP 中的执行器管理和调度，以满足 ROS 的实时要求。执行器还保证这些回调与话题、服务等消息事件协调交互。具体而言，ROS 执行时，执行器随着不同消息的到来调度一系列回调；这些执行的时间顺序可称为回调轨迹。理解回调轨迹至关重要，因为它能够反映系统的运行时行为和状态。

### 3.2 已有工具的反馈盲区

**机制概括**

- Ros2Trace/LTTng 能收集运行时数据，但主要用于事后性能分析。
- Ros2Fuzz 一次测试用户指定的单个接口，难以覆盖整个 ROS 运行时。
- Rozz 合并不同 ROS 组件的代码覆盖率。
- RoboFuzz 依靠人工总结的物理规律和应用规格作为行为预言。
- 这些方法仍缺少对整个 ROS 系统内部状态及其时间交互的实时理解。

> 性能基准工具旨在收集 ROS 运行时指标，评估资源消耗、消息吞吐量和执行时延等关键性能指标，以人工识别性能瓶颈或时序异常等运行时问题。例如，Ros2Trace 使用 Linux Trace Toolkit Next Generation（LTTng），在 ROS 运行时的不同位置插入跟踪器，以全面收集运行时行为并在之后进行深入性能刻画。`performance_test` 通过设置不同的发布/订阅配置来测量 ROS 系统性能，刻画时延、CPU 使用率和常驻内存等指标。
>
> 模糊测试为被测系统生成随机测试用例并监控异常行为。为了获得更高覆盖率并更彻底地测试被测系统，许多模糊测试器采用覆盖率引导技术：使产生新覆盖率的种子获得更高变异概率。Ros2Fuzz 建立在 AFL 之上，从目标组件提取特定 ROS 接口，生成模拟发布者或客户端的驱动并向目标组件发送载荷；但 Ros2Fuzz 只测试用户指定的接口，难以有效测试 ROS 运行时。Rozz 收集并合并不同 ROS 组件的覆盖率来指导模糊测试，从而更充分地探索 ROS 代码空间。RoboFuzz 人工总结目标 ROS 应用中的现实物理规律和已有规格，将其作为测试预言来检测潜在行为异常。然而，这些工作主要使用代码覆盖率，或人工总结目标应用和运行时组件的规格，难以理解整个 ROS 系统全面而细致的行为和状态，因而模糊测试性能相对有限。

## 4. 图 2：能覆盖代码却难以触发的挂起缺陷

**图中时序细节**

1. 图中有三条时间线：`Thread A / LpMutex`、共享的 `Wait_mutex`、`Thread B / HpMutex`。
2. Thread A 先用低优先级 `LpMutex` 锁住 `wait_mutex_`，随后尝试 `Insert Timer`，图中以圆圈叉号标为 `Failed`。
3. Thread B 的 `HpMutex` 具有更高优先级；图中依次标出 `Lock (HpMutex)`、`Higher Priority`、`Remove Timer`、`Unlock`。
4. Thread A 的 `Timer Insert` 被标记为 `Delayed`，最后才 `Unlock`。失败/延迟发生在通常很容易覆盖的执行器调度代码中，区别体现在回调时延而不是新代码分支。

**机制概括**

talker 本应每秒发布一次消息，但两个不同优先级的互斥锁共享 `wait_mutex_`，导致 Thread A 无法按时插入定时器，发布频率不规则并产生系统延迟。触发条件还要求以 service 作为输入向量且发布频率为每秒一条；普通覆盖率反馈无法识别这些内部条件。

> 本文关注整个 ROS 系统中的内存相关和并发相关缺陷，包括 ROS 运行时和 ROS 应用。然而，ROS 是为执行特定任务而设计的系统，在响应不同传入事件时往往沿着预先确定的控制路径运行，也就是说，其覆盖率变化很小。因此，代码覆盖率可能不足以反映系统状态，而测试期间不了解系统状态可能导致模糊测试性能不足。
>
> 我们使用图 2 所示的一个系统挂起缺陷进行详细说明。该缺陷在 ROS 应用启动 talker 线程和 listener 线程时触发，talker 线程被设计为每秒发布一条消息。执行期间，发布频率会不规则变化并造成意外的系统延迟。出现这种不一致，是因为 ROS 中的线程具有不同的互斥锁类别，即低优先级互斥锁 LpMutex 和高优先级互斥锁 HpMutex；二者在插入定时器回调时共享同一个 `wait_mutex_`，而定时器回调用于调度不同回调的执行。当 `wait_mutex_` 被使用低优先级互斥锁的线程 A 锁定时，它可能被使用更高优先级互斥锁的线程 B 获取。这使线程 A 无法按时插入定时器，从而造成不一致的时序行为。
>
> 该缺陷位于执行器的调度逻辑中，而这在 ROS 中是一条很容易覆盖且经常执行的代码路径。然而，以往模糊测试方法使用代码覆盖率或人工推导的预言；它们采用的引导策略无法感知这种系统内部状态变化，例如不规则的回调时延，因此难以生成能够覆盖这种错误状态的载荷。Ros2Trace 等现有基准工具虽然能够收集回调持续时间和消息吞吐量等系统内部行为，却只限于数据收集且缺少实时分析能力，因而不足以测试 ROS 系统。因此，为提高模糊测试性能并更好地捕获 ROS 内部状态变化，可以使用由回调执行时长、执行器调度和消息传递等系统交互的时间序列构成的回调轨迹来反映系统状态。通过实时刻画和分析回调轨迹，可以指导高质量载荷的生成，更全面地探索 ROS 状态空间。
>
> 这需要分析当前回调轨迹，以识别当前输入是否触发了新的状态转换。ROS 具有由各种传感器数据、控制命令和用户配置构成的巨大输入空间，因此需要生成高质量输入以进行高效测试。从示例可以看到，尽管 ROS 具有多种输入向量和配置，这个缺陷只有在使用服务作为输入向量、且发布频率为每秒一条消息时才能触发。以往方法大多使用代码覆盖率或目标应用的规格作为引导，这些信息无法深入理解 ROS 系统状态，因而生成的输入质量较低且模糊测试性能有限。因此，必须利用收集到的交互行为指导高质量输入生成，以更充分地探索 ROS 中的复杂行为。

## 5. 图 3：R2D2 的六步反馈闭环

**图中细节与机制概括**

图 3 将系统分为上半部 `Callback Trace Collection` 和下半部 `Callback Trace Guided Generation`：

1. `Registration Tracer` 与 `Runtime Tracer` 组成 Instrumentation，并插入 `ROS System Under Test`。
2. 被测系统进入 `System Execution`。
3. 执行行为流向 `Runtime Collection`。
4. 收集结果向上进入 `Callback Trace Profile` 进行聚合刻画。
5. 注册与运行信息组成 `Callback Trace`，其内部明确分为 `Callback Registration` 和 `Runtime Execution`。
6. Callback Trace 流入 `New State Identification`，再流入 `Guided Payload Synthesis`；生成的新载荷回到 `System Execution`，形成下一轮闭环。

> 为解决上述挑战，我们提出 R2D2。它利用实时行为刻画构建回调轨迹，将其作为状态标识符；之后再用该标识符指导高质量输入生成，以更充分地探索 ROS 状态空间并提高缺陷检测能力。与已有工具不同，R2D2 完全移除代码覆盖率引导，改用更有效的回调轨迹引导机制。
>
> 图 3 展示了 R2D2 的总体架构。R2D2 包含两个阶段：回调轨迹收集阶段和回调轨迹引导生成阶段。在收集阶段，R2D2 使用定制跟踪器对 ROS 运行时插桩，捕获回调执行、执行器调度和消息传递等关键系统行为。在每轮模糊测试中，插入的跟踪器记录实时执行行为，随后 R2D2 将这些记录聚合并刻画成回调轨迹。在生成阶段，R2D2 使用该轨迹作为系统状态指标，识别并优先选择能够引发新系统状态的载荷，从而改进后续载荷合成。这一迭代过程使 R2D2 能够持续生成高质量输入，优化 ROS 状态空间探索并提高整体模糊测试效率。

## 6. 运行时回调轨迹收集

### 6.1 图 4：跨 RCLCPP 与 RCL 的双路插桩

**图中细节**

- 中间主链为 `Callbacks -> RCLCPP -> RCL`。
- 绿色箭头表示注册路径：`rclcpp callback reg` 从 Callbacks 进入 RCLCPP，`rcl callback reg` 从 RCLCPP 进入 RCL；绿色数据向下写入 `Callback Registration Buffer`。
- 注册缓冲区在 RCLCPP 侧保存 `RCLCPP handlers、RCL handlers、Callback type`，在 RCL 侧保存 `RCL handlers、Callback name`。
- 黄色箭头表示运行路径：RCLCPP 记录 `RCLCPP handlers、Invoke/start/end time`；RCL 记录 `RCL handlers、Buffer size、Pub/Sub time`，二者向上写入 `Runtime Execution Buffer`。
- `callback sched` 表示 RCLCPP 执行器对 Callbacks 的调度；`rcl handle callback` 表示 RCLCPP 与 RCL 层处理器之间的对应关系。

**机制概括**

注册跟踪器负责回答“这是哪个回调、各层地址是什么”；运行跟踪器负责回答“何时被调度和执行、消息何时发布/订阅”。两类信息进入不同实时缓冲区，之后通过 handler 对齐。

> 为全面捕获 ROS 的执行行为，我们在 RCL 和 RCLCPP 层中插入不同的跟踪器。图 4 展示了插桩过程。具体而言，我们部署两类跟踪器：注册跟踪器（绿色部分）和运行时跟踪器（黄色部分）。注册跟踪器专注于捕获回调注册事件，运行时跟踪器则监控回调执行的开始点和结束点。我们还使用不同缓冲区实时取得收集到的数据。

### 6.2 Registration Tracer

**机制概括**

- `rclcpp_callback_init()`：在 ROS 应用启动并注册回调时，记录 RCLCPP handler、RCL handler 和回调类型（subscription、timer、service）。
- `rcl_callback_init()`：注册传播到 RCL 层后，补充 callback name 与 RCL handler。
- 另外需要捕获回调 namespace、不同层的分配地址和具体类型。
- 数据写入 `callback registration buffer`，供测试期间构造 callback trace。

> 注册跟踪器由不同的回调注册事件调用，用于提取多种回调属性，包括回调的命名空间、不同层中分配的地址，也就是不同的处理器，以及其具体类型，例如订阅、定时器和服务。具体而言，ROS 系统，尤其是 RCLCPP 和 RCL 层，负责注册这些回调：将其与回调名称关联，并在多个层分配对应地址，即 RCLCPP handler 和 RCL handler。为了捕获上述信息，我们同时捕获 RCLCPP 层和 RCL 层的回调注册事件，并在这两层插入两个跟踪器：`rclcpp_callback_init()` 和 `rcl_callback_init()`。
>
> ROS 应用启动时会注册不同回调，这一过程被 `rclcpp_callback_init()` 跟踪器截获；该跟踪器记录 RCLCPP handler、RCL handler 以及回调类型，即订阅、定时器或服务。注册活动随后继续传播到 RCL 层，`rcl_callback_init()` 跟踪器在这里记录额外属性，包括回调名称和 RCL handler。注册跟踪器还会把收集到的数据写入回调注册缓冲区，R2D2 在测试期间读取该缓冲区，以便构建回调轨迹。

### 6.3 Runtime Tracer

**机制概括**

- `executor_execute()`、`callback_start()`、`callback_end()`：记录目标回调的 RCLCPP handler，以及 invoke、start、end 三个时间戳。
- `rcl_take()`：记录消息传递的 RCL handler、传入消息缓冲区大小、publish/subscribe 时间戳。
- 每轮执行结束后写入 `runtime execution buffers`，再与注册信息合并。

> 运行时跟踪器用于监控系统执行行为。ROS 系统执行的核心在于执行器响应不同事件来调度回调执行，其中最常见的事件是接收消息。因此，运行时跟踪器主要监控回调调度行为和消息发布/订阅行为。
>
> 为捕获这些行为，我们使用 `executor_execute()`、`callback_start()` 和 `callback_end()` 等不同跟踪器，记录目标回调的 RCLCPP handler、调度时刻、开始时刻和结束时刻。我们还使用 `rcl_take()` 跟踪器捕获消息传递的详细信息，包括 RCL handler、传入消息缓冲区大小，以及发布和订阅活动对应的时间戳。执行阶段完成后，运行时跟踪器把聚合数据提交到运行时执行缓冲区，R2D2 再读取这些数据以构建精确的回调轨迹。收集的信息使 R2D2 能够同时全面观察 ROS 应用和 ROS 运行时，描述目标系统的结构和行为，并最终构建回调轨迹。

### 6.4 图 5：CallbackInfo、运行指标与 Callback Trace

**图中数据结构与公式**

```text
Callback Registration Info
  Callback ID        = Hash(Callback name, Callback type)
  Callback Handlers  = Union(Rclcpp handler, Rcl handler)

Runtime Execution Info
  Callback ID        = CallbackInfo.find(Rclcpp handler)
  Execution Latency  = Duration(Start time, End time)
  Scheduling Latency = Duration(Invoke time, Start time)

  Callback ID        = CallbackInfo.find(rcl handler)
  Throughput          = Buffer size / Duration(Pub time, Sub time)

Callback Trace Info
  CallTrace = Vector<Callback Latency>
  MsgTrace  = Vector<Message Latency>
```

**机制概括**

`CallbackInfo` 通过“名称 + 类型”的哈希生成稳定 ID，并保存 RCLCPP/RCL 两层 handler 的联合映射。RCLCPP handler 用于把运行记录归到回调并计算执行/调度时延；RCL handler 用于把消息记录归到回调并计算吞吐量。最终轨迹是两个可含重复元素的向量；重复代表执行器在一轮运行中多次调度同一回调。

> 收集注册信息和运行时行为后，就可以构建回调轨迹。图 5 给出了回调轨迹的总体描述。首先，原始注册数据被处理为 `CallbackInfo` 结构。这些结构包含回调标识符 ID，以及 RCLCPP handler 和 RCL handler 等不同层的对应处理器地址。回调 ID 由考虑回调名称和类型的哈希函数生成，作为区分不同回调的唯一标识符。
>
> 随后，在每轮模糊测试中，我们基于运行时数据计算两个关键指标：回调时延和消息时延。回调时延包含回调 ID、执行时延和调度时延。根据取得的 handler，并结合记录的调用时刻、执行开始时刻和执行结束时刻，计算每个回调的时延；调用时刻指执行器发出已准备执行信号的时刻。类似地，消息时延由回调 ID、消息缓冲区大小、消息发布和订阅时间戳确定，这使我们能够计算传输吞吐量。最后，将回调时延和消息时延指标合并以构建回调轨迹。该轨迹表示为两个不同向量：一个用于回调时延，另一个用于消息时延。执行期间，执行器可能多次调度同一回调，因此回调时延和消息时延中可以包含重复元素。

## 7. Callback Trace Guided Generation

### 7.1 图 6：新状态的双结构、三判据识别

**机制概括**

R2D2 持久维护两个全局结构：

- `Global Callback Graph`：保存回调调用的时间先后关系。
- `Global Callback Latency`：保存每个已见回调的平均时延和每种消息的平均吞吐量基准。

新状态满足以下任一指标：

1. 当前轨迹引入新的回调执行序列，即全局 callback graph 中出现新边。
2. 某个回调的时延显著偏离已有平均基准。
3. 某种消息的吞吐量显著低于平均基准。

**图中细节**

- 当前回调轨迹示例为 `<C1(t1), C2(t2), C1(t4), C3(t3)>`，消息轨迹为 `<M1(t1), M2(t2), M1(t4), M3(t3)>`。
- `Process` 会把重复的 `C1` 和 `M1` 聚合，得到 `<C1(t1+t4), C2(t2), C3(t3)>` 与 `<M1(t1+t4), M2(t2), M3(t3)>`。
- 左下的 callback graph 画出两条示例有向链：`C1 -> C3 -> C5 -> C6` 与 `C1 -> C2 -> C4 -> C6`，用当前序列执行 `Callback Check`；右下全局延迟向量 `<C1(Ta), C2(Tb), C3(Tc)>`、`<M1(Ta), M2(Tb), M3(Tc)>` 用于 `Latency Check`。
- 若出现新执行顺序，则向图中加入新边；若出现新回调或时延/吞吐量显著偏离，则更新全局延迟结构。

> 得到的回调轨迹包含回调与消息的执行序列，以及相关时延和吞吐量。取得当前回调轨迹后，我们首先计算轨迹中每个回调的聚合时延和每种消息的平均时延。具体而言，为感知状态变化，我们维护两个全局结构：回调图和全局回调时延。回调图表示回调调用的时间序列；全局回调时延包含总体回调时延和消息吞吐量，表示每个已遇到回调和消息的平均性能。
>
> 具体而言，我们依据以下指标识别新系统状态：第一，回调轨迹是否引入了新的执行序列，从而揭示此前未探索的交互；第二，特定回调的时延是否显著偏离已经建立的平均基准值；第三，特定消息的吞吐量是否显著低于平均基准。为建立平均基准值，我们对每个输入的时延进行若干次刻画：随机向系统生成输入、收集回调轨迹，再使用统计方法确定合适的数值。我们认为，过高或过低的基准值将分别造成状态探索不足，或发现大量无关紧要的状态变化。这两种情况可能影响整体状态识别，但对总体模糊测试性能的影响有限。
>
> 图 6 展示了识别新系统状态的过程。每个载荷执行后进行回调轨迹分析。首先，检查当前回调轨迹是否包含代表全局回调图中新边的新执行序列；如果当前回调轨迹引入了新的执行顺序，就向回调图加入相应边。随后，检查特定回调的时延是否显著超过已经建立的基准。具体而言，先从当前回调轨迹计算当前回调时延，包括消息时延和回调时延，再与全局回调时延比较，以检查是否发现新回调，或当前消息和回调的时延是否显著偏离基准。如果发现这种情况，就相应更新全局回调时延。每个新状态都用于指导后续输入生成，从而丰富对系统状态空间的探索。

### 7.2 基准值的建立

**机制概括**

论文不使用固定常数。它先随机生成输入、重复收集每个输入的 callback trace，再以统计方法得到平均基准；评估中明确采用 `2 小时`经验采样。阈值过高会漏掉状态，过低会产生大量平凡状态。

> 为建立平均基准值，我们对每个输入的时延进行若干次刻画，也就是随机向系统生成输入，收集回调轨迹，并使用统计方法确定合适的数值。我们认为，过高或过低的基准值将造成状态探索不足，或发现大量无关紧要的状态变化。

### 7.3 Guided Payload Synthesis

**机制概括**

1. Dry run：只启动系统而不发送输入，提取全部 topic/service 及其数据文件、消息类型和格式。
2. payload pool 为空：从提取的接口中随机选一个，按规格生成载荷。
3. payload pool 非空：选择此前触发新状态的载荷，根据接口规格的数据文件递归变异。
4. 执行后若触发 crash 或新状态，就把载荷保留到池中，供未来继续变异。

> 为更高效地探索 ROS 状态空间，生成符合 ROS 接口规格的载荷至关重要。然而，ROS 具有多维输入向量和高度结构化的接口，其中包括数据类型和格式各不相同的话题消息与服务请求。为解决这一问题，我们提取复杂接口规格，并据此进行引导式载荷生成。
>
> 首先，R2D2 执行一次 dry run，只启动系统而不发送任何输入，以从 ROS 系统提取全部接口规格。其中包括完整的话题和服务接口列表，以及相关数据文件、消息类型和格式。进入模糊测试阶段后，R2D2 检查当前载荷池：如果池为空，就从提取的规格中随机选择接口并据此生成载荷；否则，选择一个此前触发过新状态的载荷进行变异。变异依据接口规格中的数据文件递归进行。准备好的载荷随后被发送到 ROS 系统执行。执行后，R2D2 检查载荷是否导致系统崩溃或新系统状态；如果触发新状态或崩溃，就将该载荷保存在池中供后续迭代使用。通过这一迭代过程，R2D2 持续产生高质量载荷，更全面、深入地探索 ROS 系统状态空间。

**图中细节**

- 顶层 `Applications` 画出 Turtlesim、TurtleBot3、Autoware.AI、Navigator2 四个目标，内部部署 `Instrumented Tracer`。
- 中间 `Shared Memory` 与应用中的跟踪器双向连接。
- 底层 `R2D2 Components` 包含 `Interface Extractor`、`Process Monitor`、`System Logger`、`Payload Pool`、`Feedback Controller`、`Payload Generator`。
- `Payload Generator` 侧有一条粗箭头向上返回应用，表示反馈生成的新输入再次注入被测系统。

**机制概括**

- 核心模糊测试框架使用 Rust，跟踪器使用 C++。
- 在 Ros2Trace 基础上增加 RCLCPP/RCL tracepoint，并扩展原跟踪器以记录 buffer size 与 pub/sub 时间戳。
- RCL 初始化时分配不同共享内存缓冲区；每个共享内存对象都是由 mutex 保护的循环缓冲区，以适应 ROS 异步、高数据量运行。
- Process Monitor 监控异常退出码，用于发现崩溃、内存破坏和并发问题；System Logger 保存崩溃日志和系统统计。

> 我们使用 Rust 实现 R2D2 的核心模糊测试框架，使用 C++ 实现跟踪器。R2D2 能够对 ROS 运行时进行模糊测试，并适配了 Turtlesim、TurtleBot3、Navigator2 和 Autoware 等 ROS 应用。图 7 给出了 R2D2 的总体架构。
>
> 首先，我们扩展 Ros2Trace 的能力以刻画回调轨迹。具体而言，我们在 RCLCPP 和 RCL 层人工增加更多跟踪点，以捕获不同回调注册和消息传输等更全面的运行时行为。我们还扩展原有跟踪器，使其收集消息缓冲区大小、发布/订阅时间戳等更完整的运行时数据。此外，我们使用共享内存实时写出收集的数据。在 RCL 层初始化期间插入共享内存初始化跟踪器，分配不同的共享内存缓冲区，以记录回调执行和消息传递等不同结构的信息。为了适应 ROS 的异步特性和运行时产生的大量信息，每个共享内存对象都是一个由互斥锁保护的循环缓冲区，以保证线程安全和内存安全。
>
> 为执行模糊测试，R2D2 使用接口提取器获得全部接口规格，从而了解目标 ROS 系统能够接受哪些输入向量，并生成更全面的测试载荷。载荷生成器利用这些信息为被测系统构造载荷，插桩跟踪器则把运行时数据记录在预先分配的共享内存区域中。反馈收集器随后将这些数据刻画为回调轨迹，用于识别新系统状态并指导后续输入生成。如果 R2D2 发现某个载荷触发了新系统状态，就把它加入载荷池以供进一步变异。进程监控器检查整个 ROS 系统的运行状态并监视意外退出码，使 R2D2 能够检测目标 ROS 系统中的程序崩溃、内存破坏和并发问题。最后，R2D2 保存所有与模糊测试相关的活动日志，包括崩溃日志和系统统计。

## 9. 评估设计

### 9.1 三个研究问题

**机制概括**

- RQ1：能否发现新的 ROS 缺陷？
- RQ2：callback trace 引导是否比其他模糊测试方法进行得更深入？
- RQ3：插桩策略的性能开销是多少？

> 我们列出以下研究问题，以理解 R2D2 的性能和有效性。RQ1：R2D2 能否发现 ROS 中的新缺陷？RQ2：与其他模糊测试方法相比，R2D2 的回调轨迹引导机制能否进行更深入的测试？RQ3：R2D2 插桩策略的性能开销是多少？

### 9.2 实验设置与对照

**机制概括**

- 应用：Navigator2、TurtleBot3、Turtlesim、Autoware。
- ROS 版本：Humble（稳定且广泛使用）与 Rolling（写作时最新）。
- RQ1：Clang 编译，启用 ASAN 与 TSAN。
- RQ2：RoboFuzz、Ros2Fuzz 为基线；用 SanitizerCoverage 同时覆盖 ROS 运行时和应用；加入移除 callback trace 引导的 `R2D2-` 消融版本。
- RQ3：比较 R2D2 插桩、Ros2Trace 插桩、移除全部跟踪器的 Vanilla ROS，并用 `performance_test` 测量时延和内存。
- 基准采样 2 小时；实验在 64 核 AMD EPYC 7742 2.25 GHz、Ubuntu 22.04、Xvfb 上运行；同一硬件每次 24 小时，重复 5 次。

> 我们在四个广泛使用的 ROS 应用上评估 R2D2：Navigator2、TurtleBot3、Turtlesim 和 Autoware。目标运行时版本选择 ROS Humble 和 Rolling，因为 Humble 是最稳定且使用最广泛的 ROS 版本，而 Rolling 是写作时最新发布的版本。为回答 RQ1，我们使用 Clang 编译 ROS 运行时和 ROS 应用，并启用 ASAN 和 TSAN。为回答 RQ2 并进行全面的覆盖率比较，我们选择先进且开源的 ROS 模糊测试器 RoboFuzz 和 Ros2Fuzz 作为基线，并选择 Navigator2、TurtleBot3 和 Turtlesim 作为覆盖率比较目标。为保证公平比较，我们用 SanitizerCoverage 同时插桩 ROS 运行时和应用，从整个 ROS 系统所有被激活组件中收集覆盖率数据。为确定基准值，我们进行了 2 小时的经验采样。为进一步证明回调轨迹引导的有效性，我们实现 R2D2-，也就是移除回调轨迹引导的 R2D2，并比较 R2D2 与 R2D2- 的缺陷数量和代码覆盖率统计。为回答 RQ3，我们编译三种不同 ROS 运行时：使用 R2D2 插桩的版本、使用 Ros2Trace 插桩的版本，以及移除全部跟踪器的版本，并使用 `performance_test` 组件测量运行时时延和内存使用开销。
>
> 我们在一台配备 64 核 AMD EPYC 7742 CPU（2.25 GHz）、运行 Ubuntu 22.04 的服务器上进行评估。由于 ROS 系统通常需要图形用户界面，我们使用 X 虚拟帧缓冲区 Xvfb，在没有连接显示器的情况下进行测试。所有实验都在同一硬件上运行 24 小时并重复 5 次，遵循模糊测试评估最佳实践。

### 11.3 与 Ros2Fuzz、RoboFuzz、R2D2- 的对比机制

**机制概括**

- 相对 Ros2Fuzz：R2D2 能自动提取并测试被测系统的全部接口，而 Ros2Fuzz 一次只测试一个指定接口；平均覆盖率提升 `3.91x`。
- 相对 RoboFuzz：R2D2 用运行时 callback trace 表示状态，RoboFuzz 用特定应用的人工预言；在 TurtleBot3、Turtlesim 上分别提升 `4.08x`、`1.04x`，平均 `2.56x`。
- 相对 R2D2-：两者接口提取和载荷规格相同，唯一关键差别是 callback trace 引导。R2D2- 只发现 5 个缺陷（`#1、#3、#11、#15、#16`），平均覆盖率比 R2D2 低约 27%，说明引导机制帮助进入更深代码状态。
- R2D2- 仍超过 Ros2Fuzz/RoboFuzz，证明“自动提取全部接口 + 严格按接口规格生成输入”本身也贡献了覆盖率。

> 由表 2 可知，R2D2 在 Navigator2、TurtleBot3 和 Turtlesim 上分别达到 259111.2、111102.8 和 44576.2 的代码覆盖率，平均为 138263.4。Ros2Fuzz 在这三个目标应用上分别达到 29199.4、29394.8 和 25965.2，平均为 28186.5。与 Ros2Fuzz 相比，R2D2 的代码覆盖率分别多 7.87 倍、2.78 倍和 0.72 倍，平均提升 3.91 倍。这些提升说明 R2D2 能够生成严格符合不同输入接口结构的测试用例。Ros2Fuzz 一次只能测试一个特定接口，而 R2D2 能够全面测试被测系统包含的全部接口。回调轨迹信息提供的引导还会进一步扩大覆盖率，因为它允许探索不同系统状态，并由此发现不同代码路径。
>
> 我们还比较了 R2D2 与 RoboFuzz。RoboFuzz 未适配 Navigator2，因此只比较 TurtleBot3 和 Turtlesim。RoboFuzz 在二者上的平均代码覆盖率分别为 21867.6 和 21827.0；相比之下，R2D2 分别提升 4.08 倍和 1.04 倍。这种性能提升可以归因于回调轨迹引导向模糊测试器提供了更细致的系统状态，而 RoboFuzz 使用特定应用的预言作为系统状态。R2D2 因此能够检测目标系统内的状态转换并获得更高代码覆盖率。与 Ros2Fuzz 类似，RoboFuzz 依赖预定义接口规格测试 ROS，而自动接口提取使 R2D2 能测试更广泛的接口并覆盖更多代码。从覆盖率增长曲线看，RoboFuzz 也在测试很早阶段停止增长，反映了 ROS 固有控制流相对稳定。
>
> 为进一步研究回调轨迹引导机制的有效性，我们实现了 R2D2-，即移除回调轨迹引导的无引导版 R2D2，并在 Navigator2、TurtleBot3 和 Turtlesim 上比较二者的缺陷检测能力与代码覆盖率。对于表 1 中的全部缺陷，没有回调轨迹引导帮助时，R2D2- 只检测到 5 个缺陷，即 #1、#3、#11、#15、#16。R2D2- 发现的大多数缺陷位于相对较浅的代码路径，这说明缺少回调轨迹引导时，无论 ROS 运行时还是 ROS 应用，都很难测试到更深层的代码逻辑。表 2 显示，R2D2- 在三个目标上分别覆盖 202274.4、90843.4 和 33846.4 个分支；R2D2 相比 R2D2- 平均提升 0.27 倍。这一提升完全归因于回调轨迹引导机制，因为它能更好地感知系统中的状态转换，从而探索通常难以触发的代码段和程序状态。R2D2- 仍优于 Ros2Fuzz 和 RoboFuzz，这是因为 R2D2 能取得目标 ROS 应用拥有的全部接口，并生成严格符合输入规格的输入，也进一步说明了 R2D2 其他机制的有效性。

> 为回答 RQ3 并评估插桩对系统整体性能的影响，我们使用常用于评估 ROS 系统性能的 `performance_test` 框架。评估具体关注运行时内存使用和执行时延，并比较三种设置：R2D2 的插桩方法、Ros2Trace 的插桩方法和标准 Vanilla ROS 系统。

>
> 总体而言，R2D2 的插桩方法使内存消耗和执行时延产生了相对适中且可接受的增长。与 Ros2Trace 相近的内存使用可归因于插桩技术中的共享内存；略微增加的时延则是为支持实时数据记录能力而有意识作出的权衡。这些观察表明，回调轨迹引导机制在性能与精度之间取得了平衡，适合用于测试 ROS 系统且不会引入巨大开销。

## 13. 局限性

### 13.1 统计基准可能误判状态

**机制概括**

固定样本量可能捕获不到动态 ROS 的变化，统计离群值也会扭曲基准，造成漏识别或识别过多平凡状态。论文认为这会拖慢测试，但不会改变缺陷检测能力；未来可把文档规格等领域知识纳入基准。

> 当前，R2D2 根据运行时统计确定新状态识别的基准值。该方法能够在不同测试场景中适配并改变数值，但也存在局限。首先，ROS 系统的动态特性可能产生固定样本量无法捕获的变化。此外，一些统计离群值可能使基准偏斜，造成错误识别。这可能导致状态发现不足或识别出过多状态。虽然它可能降低测试性能，但不会影响缺陷检测能力。未来可使用文档规格等领域特定知识作为基准值，更准确、全面地分析 ROS 系统状态。

### 13.2 不能检测实时约束违例

**机制概括**

R2D2 当前能检测内存与线程相关缺陷，但不能判定违反实时约束的 timing bug；未来需要加入时序分析。

> R2D2 能够检测内存相关和线程相关缺陷。然而，ROS 是具有一定实时要求的系统，操作时机是直接影响可靠性的关键因素；时序缺陷可能导致从系统性能下降到系统完全崩溃的一系列问题。R2D2 当前无法识别与这些实时约束有关的缺陷。未来，R2D2 可以加入时序分析，从而识别可能导致实时违例的时间差异。

## 14. 结论

**机制概括**

论文的主要贡献不是新增一种覆盖率，而是用 callback trace 取代代码覆盖率作为 ROS 状态反馈：通过跨层实时插桩获得回调顺序、时延和消息吞吐量，再把新边和显著性能偏离反馈给结构化输入变异。

> 本文提出 R2D2，一种为 ROS 系统测试构建的回调轨迹引导模糊测试器。代码覆盖率引导模糊测试等传统方法通常无法捕获 ROS 系统复杂的状态转换。相比之下，R2D2 利用回调轨迹更深入地观察系统内部行为和状态。通过对 ROS 运行时进行系统化插桩，R2D2 动态监控并刻画系统状态转换，指导高质量测试用例生成。我们将 R2D2 适配到四个广泛使用的 ROS 应用。评估结果表明，R2D2 共发现 39 个缺陷，其中 6 个已被修复。与现有模糊测试器相比，R2D2 的代码覆盖率分别提高 2.56 倍和 3.91 倍，同时引入 10.4% 的执行时延开销和 1.0% 的内存消耗开销。
